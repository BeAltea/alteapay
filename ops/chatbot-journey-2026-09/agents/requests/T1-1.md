## T1 pede: ligar a projeção incremental de status logo após recordEvent

- **Arquivo alvo:** `lib/journey/events.ts` (fora do ownership de T1)
- **Motivo:** T1 entregou a projeção `negotiation_state` com duas formas equivalentes:
  `applyJourneyEventToState(event)` (incremental) e `rebuildNegotiationState(companyId)`
  (recomputo completo idempotente). Para a página de status (T5) refletir o funil em
  tempo real sem rodar rebuild a cada request, o gancho incremental deveria disparar
  toda vez que um `journey_events` é gravado com sucesso.
- **Mudança proposta:** em `recordEvent`, no ramo de sucesso (`!error` e não-duplicado),
  chamar de forma NÃO-fatal (try/catch, nunca lançar — regra D14) o gancho de projeção:

  ```ts
  // após: if (!error) return { ok: true, duplicate: false }
  // (antes do return, quando houver customerId)
  if (!error) {
    if (input.customerId) {
      try {
        const { applyJourneyEventToState } = await import("./negotiation-state")
        await applyJourneyEventToState({
          companyId: input.companyId,
          customerId: input.customerId,
          event_type: input.type,
          occurred_at: occurredAt,
          campaign_id: input.campaignId ?? null,
          session_id: input.sessionId ?? null,
          agreement_id: input.agreementId ?? null,
        })
      } catch (err) {
        console.error("[journey] projeção de status (não-fatal):", (err as Error).message)
      }
    }
    return { ok: true, duplicate: false }
  }
  ```

  Import dinâmico para não criar ciclo (`negotiation-state` → service, não importa events).
- **Bloqueia?** NÃO. Sem o gancho, `rebuildNegotiationState(companyId)` popula/reprojeta
  tudo idempotentemente (backfill e reprojeção periódica). O único efeito de não ligar é
  que a projeção não é atualizada em tempo real por evento.
